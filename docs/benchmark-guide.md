# Лаборатория Go benchmark (Go 1.22)

Сначала `make ci`, затем измерения без Delve, trace и fmt.Println в измеряемом участке. Используется обычный `for i:=0; i<b.N; i++`, без `b.Loop`. Глобальные sinks и `runtime.KeepAlive` делают результат наблюдаемым; проверки правильности идут после StopTimer. Алгоритмы со счётчиками измеряются именно в учебном виде: их константы могут отличаться от минимальных реализаций без счётчиков.

## Команды

```bash
make bench-search
make bench-sort
make bench-structures
make bench-memory
make bench-all
# Параметры одинаковы для всех групп:
make bench-all BENCHTIME=100ms BENCHCOUNT=5 BENCHCPU=1
# Быстрая проверка корректности всех веток, не измерение скорости:
make bench-all BENCHTIME=1x BENCHCOUNT=1
```

По умолчанию 100ms на подзадачу, 3 повтора, -cpu=1, -benchmem. Полная матрица занимает минуты. Не запускайте одновременно две группы, `go test -race`, компиляцию или рендеринг. `bench-all` последовательно вызывает четыре команды даже при `make -j`. 20ms допустимы для обзорного замера, но дают больше шума; для решения о производительности увеличьте время и число повторов.

## Данные и границы

`internal/dataset.GenerateRandomSlice(n)` каждый раз использует локальный rand.NewSource(7); диапазон [-1000000,1000000], n<=0 → nil. Для эксперимента с seed есть явный вариант. Сценарии:

| Имя в выводе | Точное определение |
|---|---|
| random | исходный псевдослучайный срез |
| sorted | его отсортированная копия |
| reverse | тот же набор в обратном порядке |
| nearly | sorted с одним соседним обменом на каждые 20 позиций |
| equal | только 7 |
| duplicates | random, остаток от деления на 8: значения -7…7 |

Для каждого алгоритма — собственные буферы, source не меняется. Bubble/Selection/Insertion и учебный Quick ограничены n<=512. Quick ограничен также на random, чтобы сравнения разных форм входа оставались одинаковыми. Все шесть сортировок сравниваются на n=100 и 512; Merge/slices дополнительно на n=10000. Не запускайте последний pivot на миллионе одинаковых элементов.

## Что именно входит в таймер

| Группа | Измеряемая работа | Что исключено |
|---|---|---|
| Sort/copy-sort | copy в заранее выделенный work + сама сортировка | генератор и выделение work |
| Sort/sort-only | сортировка очередного независимого буфера | копирование source в batch до 32 буферов; проверка sorted |
| Search | готовые Linear/Binary/map/slices.BinarySearch; first/middle/last/missing/duplicates | индекс и sorted данные |
| SearchBuild | map build либо allocation копии + slices.Sort | исходный генератор |
| SearchQueries | полная подготовка + q запросов с проверкой наличия | генератор и выбор целей |
| Structures | ровно одна именованная операция; размер фиксирован | восстановление до batch до 256 операций |
| Memory | построение копии среза либо индекса map | исходные данные |

В sort-only память Merge-буфера и время его выделения остаются ВНУТРИ таймера: это часть алгоритма. Batch уменьшает накладные расходы частого StopTimer/StartTimer, но нагревает кэш. Copy-sort и sort-only — разные модели; не вычитайте их медианы как точную цену copy. Сравнивайте алгоритмы внутри одной модели.

Поиск выполняется при n=100,1000,10000,100000,1000000. Отсортированный уникальный вход — `2*i`; missing=-1; duplicates — `2*(i/4)` с целью из середины. Повторяемая цель прогревает кэш и predictor; сценарий «средний элемент» не равен математическому среднему случаю. Для q=1/100/1000 запросов используется цикл целей first/middle/last/missing по несортированному random; сравнивается bool, а не исходный индекс после сортировки.

## Slice и map: договоримся о семантике

`value-lookup/slice-linear` и `value-lookup/map-key` ищут наличие числа: сравнение осмысленно, но map заранее построена. `known-index/slice-read` — контроль с другим контрактом: индекс уже известен, это НЕ поиск по значению.

Slice insert/delete ordered сохраняет порядок; map insert/delete key не имеет порядка. DeleteUnordered меняет порядок явно. Update-known-index меняет ячейку по известной позиции — отдельный контроль. В slice-update-by-key используется срез записей `{key,value}`: ищем ключ и меняем только value, сохраняя key. В map-update-key тот же ключ сохраняется, меняется value. Это сравнение обновления по ключу с линейным поиском и с готовой map, в отличие от замены самого числа в []int. Малые map-операции включают накладные расходы вызова учебной closure: не интерпретируйте различия в единицы ns как чистую стоимость runtime map.

Буферы срезов имеют cap=n+1, map создаётся с hint n+1. Измеряется вставка с подготовленным запасом, а не все варианты роста структуры. Allocation при росте append отдельно видна в построении/копировании. Размеры structures — 100 и 1000; содержимое и длина восстанавливаются вне таймера. Структуры не растут с b.N.

## Как читать результат

- ns/op — среднее время одного выполнения измеряемого тела; q-запросная строка означает всю серию q запросов.
- B/op — суммарно выделенные heap-байты на операцию; allocs/op — количество allocation. Это НЕ полный удерживаемый размер структуры и не верхняя граница стека.
- Нулевой B/op у slice-sort не означает нулевую память: work уже был выделен вне таймера, Quick использует стек.
- Нельзя по B/op определить retained heap map; в этом уроке отдельное измерение retained heap не выполняется. Для него нужны изолированный процесс, одинаковая жизнь объектов, контроль GC и сравнение heap profiles.
- Суффикс вроде -8 указывает GOMAXPROCS; при -cpu=1 он может отсутствовать. Это не число вызовов и не сложность.

Для одинакового сценария на той же машине отношение median(ns/op A)/median(ns/op B) показывает, во сколько раз B быстрее A. Не делите результаты разных режимов, q или размеров. Сравните тенденцию при увеличении n и разницу allocation. Benchmark не доказывает Big O: это конечное измерение с кэшем, GC, compiler и шумом; асимптотика выводится из числа операций.

Для анализа нескольких запусков можно использовать [benchstat](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat); он не является зависимостью проекта и не требуется для make. Реальные сырые результаты, окружение и медианы лежат в [benchmarks/](benchmarks/README.md).
