# Лаборатория Go benchmark (Go 1.22)

Сначала `make ci`, затем измерения без Delve, trace и fmt.Println в измеряемом участке. Используется обычный `for i:=0; i<b.N; i++`, без `b.Loop`. Глобальные sinks и `runtime.KeepAlive` делают результат наблюдаемым; проверки правильности идут после StopTimer. Алгоритмы со счётчиками измеряются именно в учебном виде: их константы могут отличаться от минимальных реализаций без счётчиков.

## Команды и формат отчёта

```bash
# Быстрый понятный пример: один размер, одна цель, три прогона.
make bench-search BENCHN=100 BENCHSCENARIO=last BENCHTIME=20ms
# Все пять размеров и пять целей измеряются; compact показывает last.
make bench-search
make bench-search BENCHVIEW=full
# Подготовка и полная задача теперь имеют собственные команды.
make bench-search-build
make bench-search-queries
make bench-sort
make bench-structures
make bench-memory
# Все шесть групп последовательно, даже при make -j.
make bench-all
# Те же testing.B без таблиц:
make bench-search-raw
make bench-search-build-raw
make bench-search-queries-raw
make bench-sort-raw
make bench-structures-raw
make bench-memory-raw
make bench-all-raw
# Более тщательное измерение:
make bench-search BENCHTIME=500ms BENCHCOUNT=5 BENCHCPU=1
# Только проверка корректности веток и wiring:
make bench-all BENCHTIME=1x BENCHCOUNT=1
```

По умолчанию 100ms на подзадачу, три прогона, `-cpu=1`, `-benchmem`.
Полная матрица занимает минуты. Не запускайте одновременно другие группы,
`go test -race`, компиляцию или рендеринг. 20ms подходит для демонстрации формата,
но даёт больше шума; для вывода о скорости увеличьте время и число прогонов.
`1x` проверяет один вызов без калибровки и не подходит для ранжирования скорости.

`BENCHN=0` оставляет все размеры; `BENCHN=100` выбирает только этот размер
до измерения. Если размера в группе нет, команда завершится ошибкой «нет
измерений», а не нарисует нули. `BENCHSCENARIO` применим только к search/sort.
У Structures разная глубина имён b.Run: фильтр размера передаётся через
`LESSON7_BENCH_N` и проверяется до подготовки данных, вне таймера. Без фильтра
выполняется исходная матрица. Не задавайте эту служебную переменную вручную.

В компактном виде поиска показывается `last`, сортировки — `random`, когда
они присутствуют. Если выбран только `first` или `sorted`, показывается именно
выбранный сценарий. Остальные измерения не удаляются: в сообщении указано число
скрытых агрегированных строк, все они остаются в CSV. `BENCHVIEW=full` меняет
только представление, не набор измерений. Индексные и q-серии не сокращаются.

`cmd/benchreport` не реализует второй benchmark. Он запускает прежний
`go test ./internal/benchmarkdebug`, сохраняет raw и разбирает его stdlib-парсером.
На каждой комбинации алгоритма/сценария/режима/n/q/окружения/GOMAXPROCS берётся
**среднее арифметическое** `ns/op`, `B/op`, `allocs/op` по `-count` прогонам.
Прогоны имеют равный вес: `b.N` не усредняется и не является весом.
CSV также содержит медиану, минимум и максимум ns/op, количество прогонов.
Средние вычисляются из напечатанных Go значений с их исходным округлением.

Каждый запуск создаёт отдельный каталог в `bin/benchmarks/` (переопределяется
через `BENCHDIR`). Внутри `raw.txt`, `summary.csv`, `report.md`,
`environment.json`. Raw-команды также сохраняют эти файлы. Ошибка процесса,
повреждённая строка, отсутствующий PASS/итоговая ok или неверное число повторов
дают ненулевой exit и **не публикуют частичную таблицу как успешную**. Raw остаётся
для диагностики. `make clean` удаляет bin; сохраняйте нужные запуски отдельно.

Для повторного форматирования одного завершённого raw без новых измерений:

```bash
go run ./cmd/benchreport -input bin/benchmarks/ИМЯ_ЗАПУСКА/raw.txt -count 3 -view full
```

Замените ИМЯ_ЗАПУСКА путём, напечатанным после вашей команды. Импорт принимает
чистый вывод **одного** go test, с заголовками окружения, PASS и итоговой ok.
Команды shell, объединённые логи нескольких запусков и прерванные логи нужно
исследовать отдельно; они отклоняются. `-count 0` допустим только для импорта,
если число повторов неизвестно: проверка количества отключается явно, фактическое
k видно в каждой строке. Версия Go и benchtime не угадываются из raw.
Исходный файл при импорте не меняется. Флаги kind/n/scenario относятся к новым
измерениям; импорт читает все имена из файла.

## Данные и границы

`internal/dataset.GenerateRandomSlice(n)` каждый раз использует локальный rand.NewSource(7); диапазон [-1000000,1000000], n<=0 → nil. Для эксперимента с seed есть явный вариант. Сценарии:

| Имя в выводе | Точное определение |
|---|---|
| random | исходный псевдослучайный срез |
| sorted | его отсортированная копия |
| reverse | тот же набор в обратном порядке |
| nearly | sorted с одним соседним обменом на каждые 20 позиций |
| equal | только 7 |
| duplicates | random, остаток от деления на 8: значения -7…7 |

Для каждого алгоритма — собственные буферы, source не меняется. Bubble/Selection/Insertion и учебный Quick ограничены n<=512. Quick ограничен также на random, чтобы сравнения разных форм входа оставались одинаковыми. Все шесть сортировок сравниваются на n=100 и 512; Merge/slices дополнительно на n=10000. Не запускайте последний pivot на миллионе одинаковых элементов.

## Что именно входит в таймер

| Группа | Измеряемая работа | Что исключено |
|---|---|---|
| Sort/copy-sort | copy в заранее выделенный work + сама сортировка | генератор и выделение work |
| Sort/sort-only | сортировка очередного независимого буфера | копирование source в batch до 32 буферов; проверка sorted |
| Search | готовые Linear/Binary/map/slices.BinarySearch; first/middle/last/missing/duplicates | индекс и sorted данные |
| SearchBuild | map build либо allocation копии + slices.Sort | исходный генератор |
| SearchQueries | полная подготовка + q запросов с проверкой наличия | генератор и выбор целей |
| Structures | ровно одна именованная операция; размер фиксирован | восстановление до batch до 256 операций |
| Memory | построение копии среза либо индекса map | исходные данные |

В sort-only память Merge-буфера и время его выделения остаются ВНУТРИ таймера: это часть алгоритма. Batch уменьшает накладные расходы частого StopTimer/StartTimer, но нагревает кэш. Copy-sort и sort-only — разные модели; не вычитайте их средние как точную цену copy. Сравнивайте алгоритмы внутри одной модели.

Поиск выполняется при n=100,1000,10000,100000,1000000. Отсортированный уникальный вход — `2*i`; missing=-1; duplicates — `2*(i/4)` с целью из середины. Повторяемая цель прогревает кэш и predictor; сценарий «средний элемент» не равен математическому среднему случаю. Для q=1/100/1000 запросов используется цикл целей first/middle/last/missing по несортированному random; сравнивается bool, а не исходный индекс после сортировки.

## Slice и map: договоримся о семантике

`value-lookup/slice-linear` и `value-lookup/map-key` ищут наличие числа: сравнение осмысленно, но map заранее построена. `known-index/slice-read` — контроль с другим контрактом: индекс уже известен, это НЕ поиск по значению.

Slice insert/delete ordered сохраняет порядок; map insert/delete key не имеет порядка. DeleteUnordered меняет порядок явно. Update-known-index меняет ячейку по известной позиции — отдельный контроль. В slice-update-by-key используется срез записей `{key,value}`: ищем ключ и меняем только value, сохраняя key. В map-update-key тот же ключ сохраняется, меняется value. Это сравнение обновления по ключу с линейным поиском и с готовой map, в отличие от замены самого числа в []int. Малые map-операции включают накладные расходы вызова учебной closure: не интерпретируйте различия в единицы ns как чистую стоимость runtime map.

Буферы срезов имеют cap=n+1, map создаётся с hint n+1. Измеряется вставка с подготовленным запасом, а не все варианты роста структуры. Allocation при росте append отдельно видна в построении/копировании. Размеры structures — 100 и 1000; содержимое и длина восстанавливаются вне таймера. Структуры не растут с b.N.

## Как читать результат

```text
BenchmarkSearch/linear/first/n=100  98816059  1.136 ns/op  0 B/op  0 allocs/op
```

Это иллюстрация формата из исходного лога, не результат нового запуска.

| Поле | Значение |
| --- | --- |
| `n=100` | Длина входного массива: 100 элементов |
| `98816059` | `b.N`: автоматически подобранное число вызовов внутри одного прогона, не длина, сравнения или Big O |
| `1.136 ns/op` | Среднее время **полного поиска** в одном прогоне; не цена одного элемента |
| `0 B/op` | Напечатанное число выделенных heap-байт на op; готовые данные и стек сюда не входят |
| `0 allocs/op` | Напечатанное число heap allocations на op |
| `-count=3` | Три отдельных результата; внутри каждого своё b.N, возможно миллионы вызовов |

`testing.B` делит измеренные время и allocation на число операций. В Go 1.22
`B/op` и `allocs/op` печатаются после целочисленного деления: редкая allocation
может округлиться до нуля. Новая таблица усредняет уже опубликованные метрики,
а не восстанавливает потерянные дробные части. ns/op SearchQueries означает
всю подготовку и **все q запросов**; на n или q его не умножают.

Нулевой B/op у сортировки не означает нулевую память: work был выделен вне
таймера, Quick использует рекурсивный стек. Отчёт разделяет:

1. Расчётный размер элементов исходного `[]int`: `n*sizeof(int)` по GOARCH
   самого лога (для amd64/arm64 8 байт, для 386/arm 4). Не включены header,
   запас cap, map-индекс, batch рабочих буферов и другие накладные расходы.
2. Измеренные heap allocation/op — B/op и allocs/op.
3. Теоретическую дополнительную память: итеративный поиск O(1), готовый индекс
   map O(n), Merge буфер O(n) + стек O(log n), Quick стек обычно O(log n),
   в худшем O(n). Столбец lookup показывает память операции сверх готового индекса.

Это **не** формула `total=B/op+n*8`. Retained heap и peak heap здесь не
измеряются: для них нужны отдельный процесс, контроль времени жизни и GC,
heap profiles и учёт погрешности. Размеры slice/map нельзя сравнить только
по allocation одной уже подготовленной операции.

Суффикс `-8` — GOMAXPROCS, при 1 он может отсутствовать. Это не число
вызовов. Строки с разными CPU, GOOS/GOARCH, пакетом, GOMAXPROCS, n, q,
сценарием или режимом не агрегируются вместе. Параметры и версия Go сохраняются
для каждого запуска; логи разных запусков не склеиваются автоматически.

Единицы времени выбираются ns/µs/ms/s, памяти B/KiB/MiB/GiB, явно на каждой
строке. Четыре значащие цифры сохраняют различия быстрых алгоритмов, но не
создают доказательства статистической значимости. `Heap / op` — средний B/op,
а `Время: теория` — подписанная верхняя или ожидаемая оценка; первые/средние
цели могут попадать в лучший случай. Binary на middle этого набора сразу
попадает в target; slices.BinarySearch продолжает искать нижнюю границу.

Внутри одинакового сценария, n, q и режима на той же машине отношение
**mean(A)/mean(B)** показывает, во сколько раз среднее A больше B именно здесь.
Отчёт показывает min и max/min только для сопоставимых контрактов: готовый
поиск, серия с подготовкой, сортировки одного режима, поиск/обновление по ключу.
Не объявляется общий победитель для ordered slice insert и unordered map insert,
для чтения известного индекса и поиска значения, либо двух разных результатов
построения структуры. Min/max отдельных прогонов сохраняются в CSV;
различие средних само по себе не означает статистически значимого преимущества.

Повторяемые lookup targets, прогрев cache/predictor, inlining, учебные счётчики,
запись global sink, вызов closure и таймер влияют на наносекундные операции.
Результат используется и проверяется вне таймера, поэтому полностью удалить
измеряемую работу как неиспользуемую компилятор не может; это не делает замер
«чистой стоимостью инструкции». Не вычитайте пустой цикл как универсальную
поправку. Для модели разных запросов используйте SearchQueries, учитывая,
что q=1 здесь выполняет только first — это выгодный случай Linear.

Benchmark показывает конечный опыт на конкретной машине, **не доказывает Big O**.
Асимптотика следует из числа операций при росте входа. Ожидаемое O(1) у map —
не гарантия худшего случая; учебный Quick с последним pivot не эквивалентен
slices.Sort. Оценки slices.Sort относятся к реализации Go 1.22; не переносите
детали runtime между версиями как вечный API-контракт.

Для статистического анализа можно отдельно использовать
[benchstat](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat); он не является
зависимостью проекта. Старые [результаты](benchmarks/README.md) явно подписаны
как исторические медианы. Новые команды вычисляют арифметические средние.
